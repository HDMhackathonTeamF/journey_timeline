1. 経路検索（planning グループ）
乗換案内のコアとなる経路検索を行います。

GET /api/v1/plan

できること: 出発・到着・始発・終電といった条件に基づく基本的な経路検索を行います。

必要な情報（主なクエリパラメータ）:

from (必須): 出発地の駅ID、または座標（geo:lat,lng）。

to (必須): 目的地の駅ID、または座標。

date: 日付（YYYYMMDD形式）。

time: 時刻（HH:MM形式）。

type: 検索タイプ（departure 出発, arrival 到着, first 始発, last 終電）。

via: 経由地（駅IDまたは座標。最大3つまで指定可能）。

maxTransfers / numItineraries: 許容する最大乗換回数（デフォルト3）と、取得する経路の候補数（デフォルト3）。

allowModes / avoidModes: 利用する/しない交通手段（rail, bus, air など）。

avoidWalk: 徒歩区間を除外するかどうか（true / false）。

GET /api/v1/guidance/plan

できること: 上記の基本機能に加え、フロントエンドのUI表示（経路案内）に特化した高度な情報を返します。経路のランク付け、比較指標、地図に描画するためのジオメトリ（線情報）などが含まれます。

必要な情報: plan と共通のパラメータに加え、以下の指定が可能です。

strategy: 最適化の優先基準（balanced バランス, fastest 最速, fewestTransfers 最小乗換, lowestFare 最安, shortestWalk 最短徒歩）。

live: リアルタイムの運行情報を加味するか（true / false）。

2. 検索・サジェスト（search グループ）
駅名や場所の名前を入力する際のオートコンプリート機能を提供します。

GET /api/v1/locations/suggest

できること: 駅名に特化したサジェスト（入力補完）や曖昧回避を行います。

必要な情報: q (検索キーワード)、limit (取得件数)。

GET /api/v1/places/suggest

できること: 駅だけでなく、停留所、施設、住所などを含む広範な場所のサジェストを行います。

必要な情報: q (検索キーワード)、limit (取得件数)。

GET /api/v1/places/reverse

できること: 地図上で選択した座標（ポイント）の周辺にある場所情報を取得するリバースジオコーディングを行います。

3. 駅情報（stations グループ）
特定の駅に関する情報を取得します。

GET /api/v1/stations/{id}

できること: パスパラメータで指定した駅の詳細情報を取得します。

GET /api/v1/stations/{id}/departures

できること: 指定した駅の出発案内（駅の時刻表・発車標データ）を取得します。

必要な情報: date (日付)、time (時刻)、limit (取得件数)。

4. カタログ情報（catalog グループ）
システムが保持している事業者等のメタデータを取得します。

GET /api/v1/feeds

できること: 交通事業者などが提供しているデータフィードの一覧を取得します。

GET /api/v1/operators

できること: 運行会社（オペレーター）の一覧情報を取得します。

5. 地図データ（map グループ）
地図描画に特化したデータを提供します。

GET /api/v1/route-map

できること: 路線図を描画するためのデータを取得します。

GET /api/v1/map/3d-scene

できること: 3Dマップシーンを描画するための構成データを取得します。

6. システム状態（system グループ）
GET /api/health

できること: APIサーバーの死活監視（正常に稼働しているかどうかのヘルスチェック）に使用します。

## 💡 【重要】Transit API 実装・連携における知見と仕様

APIの実際の挙動検証（スパイクテスト）により判明した、フロントエンドとバックエンドを連携させる上での極めて重要な仕様とワークフローです。

### 1. 経路検索（plan）には「駅の文字列（名前）」ではなく「一意のID」が必須
`GET /api/v1/plan` などの `from` や `to` パラメータに「東京」や「新宿」といった文字列を直接渡すと `404 stationNotFound` エラーになります。
経路検索を行う前に、必ず **サジェストAPI（`locations/suggest` や `places/suggest`）** を叩いて特定の「ID（例: `scrape-jreast-...`）」を取得し、そのIDを検索条件として渡す必要があります。

### 2. 「同じ駅名」でも「路線ごと」にIDが異なる
「新宿」でサジェストAPIを叩くと、「JR中央本線の新宿駅」「JR埼京線の新宿駅」など、**路線ごとに別々の駅ID** が複数返却されます。
そのため、バックエンドで勝手に最初の候補を選ぶのではなく、**フロントエンドのUI（オートコンプリート等）でユーザー自身に正しい路線・駅（ID）を選択させる** アプローチが必須となります。

### 3. 電車・バス・飛行機のマルチモーダル検索に対応
Transit API は電車専用ではありません。
`allowModes` パラメータで指定可能な通り、**バス停（kind: stop）** や **空港・フライト（kind: station, JAL/ANA等のfeedId）** も `places/suggest` APIから検索可能です。
これにより、「自宅近くのバス停 ⇨ 羽田空港 ⇨ 現地の空港」といった高度な経路検索も実現できます。

### 📌 フロントエンド ⇄ バックエンドの実装ワークフロー（結論）

経路（Transit）を作成する際の具体的な手順は以下の通りです。

1. **【フロントエンド】**: ユーザーが出発地・到着地の文字列を入力。
2. **【フロントエンド ⇨ バックエンド ⇨ Transit API】**: サジェストAPIを呼び出し、駅・バス停・空港の候補一覧（IDと名称のセット）を取得してドロップダウンで提示。
3. **【フロントエンド】**: ユーザーが正確な候補を選択し、アプリがその **「ID」** を保持する。
4. **【フロントエンド ⇨ バックエンド ⇨ Transit API】**: 保持した「出発地ID」と「到着地ID」を使って経路検索（Plan）APIを呼び出す。
5. **【バックエンド】**: APIから返ってきた複雑な経路データを、アプリのタイムライン表示用に成型してフロントエンドに返す。

## Transit APIを用いた経路検索システム仕様まとめ

### 1. 検索対象と入力の柔軟性
Transit APIの最大の強みは、駅などの「交通拠点」だけでなく、「任意のロケーション（観光地、ホテル、施設など）」をシームレスに組み合わせて検索できる点です。
* **入力形式の混在**: 出発地(from)と目的地(to)には、駅ID（feedId:stopId）だけでなく、緯度・経度の座標（geo:lat,lng）を直接指定可能です。
* **ドア・ツー・ドア検索**: 観光施設などの座標を指定した場合、API側で「現在地から最寄り駅までの徒歩移動」や「降車駅から目的地までの徒歩移動」を自動的に算出し、交通機関と組み合わせた完全なルートを返します。
* **対応交通機関**: 電車（JR、私鉄、新幹線等）に限らず、バス、飛行機、フェリー、徒歩など、あらゆる移動手段が検索対象に含まれます。

### 2. 検索条件の指定（オプション）
ユーザーの要望に応じた細かな絞り込み検索が可能です。
* **日時の指定**: 指定した日付・時刻に基づく検索（出発時間、到着時間、始発、終電の指定）が可能です。
* **交通手段の制御**: パラメータ（allowModes, avoidModes）を用いることで、「電車のみ」「飛行機を利用しない」といった交通手段の限定が可能です。
* **その他の制御**: 経由地の指定、徒歩の回避、許容する最大乗換回数の制限などが可能です。

### 3. 推奨するUI/UXアプローチ（複数パターンの自動提示）
ハッカソンにおける限られた開発期間と、直感的な旅程作成というプロジェクトの目的を考慮し、ユーザーに複雑なオプションを入力させる方式よりも、以下の「早・安・楽 方式」を推奨します。
* **シンプルな入力**: ユーザーには「出発地（または座標）」「目的地（または座標）」「時間」のみを入力させます。
* **バックエンドでの一括計算**: バックエンドのプロキシAPIが上位の経路検索API（`/api/v1/guidance/plan` 等）を呼び出し、「最速ルート」「最安ルート」「乗換最小ルート」といった異なる最適化基準（strategy）に基づく複数の結果を一括で取得します。
* **UIでの選択**: フロントエンドでは、取得した複数パターンの経路をカテゴリ別に整理して提示し、ユーザーにワンクリックで選ばせます。

### 4. バックエンド（プロキシ）の役割
このシステムにおいて、バックエンドはBFF（Backends For Frontends）として以下の重要な役割を担います。
* **テキストから座標への変換**: ユーザーが入力した「施設名」を、Transit APIのサジェスト機能（`/api/v1/places/suggest`）等を用いて裏側で座標に変換し、経路検索APIに渡す処理を担う想定です。
* **データの成型**: Transit APIが返す複雑な生データや、システム上扱いづらい時刻データ（サービス日からの経過秒数など）を、フロントエンドの表示に最適な形式（出発・到着時刻のフォーマット化、運賃の合算、路線名の抽出など）に成型した上で返却します。
* **将来の拡張**: 検索条件やロジックがバックエンドに集約されているため、将来的な機能拡張（特定の交通手段を除外するオプションの追加など）への対応が容易になります。

## 将来実装する拡張機能・オプションの検証結果まとめ

将来的にUI/UXをさらに向上させるため、以下の高度な検索オプションをバックエンド・フロントエンドに順次実装していく予定です。

### ① 「自分が活きたい土地を入力すると適切な経路(電車・バス・空港全て検案)を調べる」
* **検証**: 可能ですが、システム上の工夫が必要です。
* **理由**: 経路検索API（`/api/v1/plan`）は、必ず「出発地（from）」と「目的地（to）」の両方を必要とします。そのため、目的地（行きたい土地）だけでなく、出発地（現在地やホテルなど）も一緒に指定する必要があります。
* **補足**: 単なる「土地の名前」ではAPIが正確な位置を認識できない場合があります。この場合、ユーザーが土地の名前を入力した際に、バックエンドで「検索・サジェストAPI（`/api/v1/places/suggest`）」を呼び出して正確な駅IDや座標（`geo:lat,lng`）に変換してから、経路検索APIに渡すというフローになります。デフォルトでは電車・バス・飛行機などがすべて検索対象になります。

### ② 「出発時間や到着時間(日時)を入力すると適切な経路(電車・バス・空港全て検案)を調べる」
* **検証**: 完全に可能です。
* **理由**: APIには日付（`date`：YYYYMMDD形式）と時刻（`time`：HH:MM形式）を指定するパラメータが用意されています。これらに加え、検索タイプ（`type`）として `departure`（この時間に出発したい）または `arrival`（この時間に到着したい）を指定することで、ピンポイントでの経路検索が可能です。

### ③ 「①，②において候補を電車のみなどに絞る」
* **検証**: 完全に可能です。
* **理由**: APIには利用する交通手段を制御するパラメータとして、`allowModes`（許可する交通手段）と `avoidModes`（除外する交通手段）が用意されています。ここに `rail`（鉄道）だけを指定することで「電車のみ」に絞り込むことが可能です。他にも `bus`（バス）、`air`（飛行機）などを組み合わせて柔軟に制御できます。

### その他に可能な調べ方（Transit APIのオプション機能）
上記の基本検索に加えて、パラメータを組み合わせることで以下のような調べ方（絞り込み・条件追加）が可能であり、将来的な機能拡張の候補とします。

* **「経由地」を指定した検索**
  出発地と目的地の間に「ここを通って行きたい」という経由地（`via` パラメータ）を最大3か所まで指定してルートを組むことができます。
* **「始発」や「終電」の検索**
  時刻を指定するのではなく、検索タイプ（`type`）に `first`（始発）や `last`（終電）を指定することで、その日の最初・最後の移動ルートを調べることができます。
* **「乗換回数」の上限を設けた検索**
  「乗り換えは多くても1回までが良い」という場合、`maxTransfers` パラメータで許容する最大乗換回数を制限できます。
* **「徒歩」を避ける検索**
  駅から駅への移動などで、なるべく歩きたくない場合に `avoidWalk=true` を指定することで、極力徒歩を排除したルートを検索させることができます。
* **「優先基準」を変えた検索（BFF向けの高度なAPI利用時）**
  `/api/v1/guidance/plan` という上位APIを使用した場合、`strategy` パラメータを使うことで、「最安（`lowestFare`）」「最短所要時間（`fastest`）」「乗換回数最小（`fewestTransfers`）」「徒歩距離最小（`shortestWalk`）」など、何を最優先にしてルートを提示するかを指示できます。
